Deploy ESXi, step by step

Tick each step as you finish it. Version details vary, so check Broadcom’s documentation for your release.

  1. Check hardware and requirements

    Confirm a 64-bit CPU with virtualization enabled in BIOS/UEFI, enough RAM, a boot disk, and a NIC listed on the VMware compatibility guide.

  2. Download the ESXi ISO

    Get the installer ISO and your license from the Broadcom support portal. Write it to a USB drive with a tool like Rufus, or mount it through the server’s remote console (iDRAC, iLO).

  3. Boot the installer

    Boot from the USB or ISO and choose the ESXi installer. Accept the license agreement with F11.

  4. Select the install disk and set the root password

    Pick the target disk, choose a keyboard layout, set a strong root password, then confirm with F11. Remove the media and reboot.

  5. Configure the management network

    In the console (DCUI) press F2, then Configure Management Network. Set a static IP, subnet mask, gateway, DNS, hostname and VLAN if needed. Run a network test.

  6. Open the ESXi Host Client

    Browse to https://<ESXi-IP>/ui and log in as root. Apply your license. The host is now ready to run VMs on its own.

  7. Deploy vCenter Server (management)

    Run the vCenter installer from another machine and deploy the appliance onto the ESXi host. vCenter is itself a VM and does not run your workloads.

  8. Build the inventory

    In vCenter create a Datacenter, add a Cluster, then add each ESXi host. Optionally enable HA, DRS and vMotion, and create Resource Pools.

  9. Configure networking

    Create a vSwitch (standard or distributed), attach physical NICs (pNIC) and add Port Groups for your VMs.

  10. Configure storage

    Create a Datastore on VMFS, NFS or vSAN so VM disks (VMDK) have capacity.

  11. Create your first VM

    Choose a host or cluster, set vCPU and vRAM, add a vDisk on your datastore, connect the vNIC to a port group, mount an OS ISO and power it on.

Lab 1: build an ICS/OT cyber range on your ESXi host

Once ESXi is deployed, you can turn the same host into an isolated attack-and-defend lab: an attacker zone, an OT management zone and a production-process simulation, all stitched together on one private network.

Isolated topology

VMnet1 - isolated bridge (host-only)
Attacker Zone→Firewall VM→OT Management
Firewall VM→Production Simulation
No connection to the physical network

What runs where

  • Attacker Zone — Kali Linux, with exploit and protocol-fuzzing scripts aimed at the lab only
  • Firewall VM — a virtual firewall (e.g. pfSense/OPNsense) with two vNICs, segmenting the Attacker Zone from the OT side and logging every rule hit
  • OT Management — a Windows Server, a SIEM host, and an OT-protocol monitoring VM for alerts and protocol analysis
  • Production Simulation — a PLC/EWS simulator and a SCADA visualization VM standing in for the real process

Deploy the lab VMs

  1. Isolate the network first

    On the ESXi host, create a private vSwitch and port group with no physical NIC attached (a host-only network). This becomes your isolated bridge; nothing on it can reach your production network or the internet.

  2. Build the attacker zone

    Deploy a Kali Linux VM and attach its vNIC only to the isolated port group. Keep offensive tooling (recon and exploit scripts) confined to this VM so it never touches anything outside the lab.

  3. Add a firewall VM

    Deploy a small firewall appliance (pfSense or OPNsense) with two vNICs: one facing the Attacker Zone, one facing the OT side. Write rules that only allow the traffic you want to study through, and log everything so you can see exactly what the firewall blocked or passed during an exercise.

  4. Build the OT management zone

    Deploy a Windows Server VM plus a SIEM/monitoring VM for protocol analysis and alert parsing. Attach both to the same isolated port group so they can see lab traffic but nothing else.

  5. Build the production simulation

    Deploy a PLC or EWS simulator alongside a SCADA visualization VM to stand in for a real industrial process. Connect them to the isolated port group as well.

  6. Mirror traffic to your SIEM

    Configure port mirroring (or a span-style capture) on the isolated port group so the monitoring VM can see every packet the attacker VM sends toward the simulated PLC.

  7. Run a contained exercise

    From the attacker VM, scan and probe the simulated OT protocol (for example Modbus). Watch the SIEM move from standby to active alerts, and correlate what it saw with what you actually sent.

  8. Snapshot before you start

    Take a snapshot of every VM before each exercise so you can revert the whole lab to a clean, isolated standby state afterward.

Safety: keep this port group host-only, with no uplink to a physical NIC. An OT cyber range with a bridge to your real network or the internet stops being a lab.

Lab 2: ICS/OT hardware lab — Rockwell 1794-AENTR Flex I/O

A small, physical ICS/OT lab: a Rockwell Automation 1794-AENTR Flex I/O Ethernet adapter and a Raspberry Pi running Kali Linux, wired together on their own isolated network. Used to baseline communication, run controlled reconnaissance, capture traffic and analyze device behavior — never against production equipment.

Lab network plan

  • 1794-AENTR — 192.168.169.60 / 255.255.255.0 (target Flex I/O adapter)
  • Raspberry Pi / Kali — 192.168.169.100/24 (security workstation)
  • HTTP — TCP 80, management web interface
  • EtherNet/IP — TCP 44818

Tools on Kali

  • nmap — identify exposed TCP services
  • Wireshark — capture and inspect packets (PCAPNG)
  • Scapy — programmatic packet analysis
  • pycomm3 — EtherNet/IP experimentation
  • Python venv — isolate project dependencies

Run the lab

  1. Wire up and isolate

    Connect the 1794-AENTR and the Raspberry Pi to their own unmanaged switch, with no uplink to production, corporate or home networks. Keep the segment physically and logically separate.

  2. Configure the Kali interface

    Set a static address on the lab interface:

    sudo ip addr flush dev eth0
    sudo ip addr add 192.168.169.100/24 dev eth0
    sudo ip link set dev eth0 up

  3. Verify connectivity

    Ping the adapter: ping -c 4 192.168.169.60. Expect replies with no packet loss before doing anything else.

  4. Set up a Python environment

    Create a virtual environment so lab dependencies never touch the system Python: python3 -m venv myenv then source myenv/bin/activate.

  5. Run controlled reconnaissance

    Scan every TCP port: nmap -Pn -sS -p 1-65535 192.168.169.60. On this lab the baseline is 80/tcp open (HTTP) and 44818/tcp open (EtherNet/IP-2). Save the command, timestamp and output as evidence.

  6. Capture traffic in Wireshark

    Capture on the lab interface and save as PCAPNG. Useful filters: ip.addr == 192.168.169.60, tcp.port == 80, tcp.port == 44818. Watch connection setup/teardown, HTTP behavior, EtherNet/IP traffic and any resets.

  7. Run a bounded, rate-limited test

    Send a finite, slow burst of HTTP requests (for example 20 requests, a quarter-second apart) instead of an unbounded flood, while you watch the device and the packet capture. Stop immediately on device instability, loss of the web interface, unexpected I/O behavior, or any traffic leaving the isolated network.

  8. Analyze the capture with Scapy

    Load the PCAPNG, count packet types, and inspect TCP SYN and RST flags. Filter by the correct destination — the 1794-AENTR at 192.168.169.60, not the Kali host — before treating any count as device-directed traffic.

  9. Visualize and report

    Chart the protocol distribution with matplotlib, then write up the test objective, topology and addressing, baseline state, exact procedure and timestamps, packet-level observations, device behavior, and the evidence files (PCAPNG, terminal output, screenshots, logs).

  10. Apply defensive recommendations

    Restrict the HTTP management interface and EtherNet/IP exposure to authorized engineering networks, segment the control network, monitor connection rates and TCP anomalies against your baseline, and use OT-aware monitoring with validated protocol dissectors.

Safety: test only equipment you own or are explicitly authorized to test, on a network kept physically and logically isolated from production. A SYN or packet count of zero is not proof of absence — validate flag logic and destination addressing before drawing conclusions. Availability and safety come before experimentation.
